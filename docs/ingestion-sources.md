# 来源与入库：多条通道，一个产品表

> 2026-11-05 定稿。这份文档存在的唯一目的：**下次不必再重新讨论「来源该怎么建模」**。
> 产品数据从来不是只有 78dm 一条通道，`review_items` 只是其中一条通道的收件箱。

## 结论先行

1. **来源是复数。** 当前至少五条通道：78dm 爬取、B站视频（ASR + LLM 抽取）、百度百科等网页整理、
   agent 网络搜索（未落地）、人工录入。它们的产出**汇入同一张 `products`**，没有第二张产品表。
2. **`review_items` 是「视频来源专用收件箱」，不是核心流程。** 侧栏归在「来源」分组下。
   它的存在是为了保留「这条 mention 从哪个视频第几秒来、怎么处理的」，不是为了给全库做闸门。
3. **事件 / 资讯是另一件事。** 未来的 `news` / `events` 表独立存在，**只引用 `products`**，
   不反向塞进 `products`，也不塞进 `review_items`。
4. **`aliases` 稀疏是正常的。** 它只记录「外部来源的原标题」，只有走过外部同步的行才有值。
   覆盖率不是指标，缺失不是缺陷。
5. **`products.source` 目前仍是自由文本。** 已知它混着渠道名与出处 URL，暂不结构化的理由见第五节。

## 一、来源清单

| 来源 | 现状 | 落库路径 | 典型产出 |
| --- | --- | --- | --- |
| 78dm 爬取 | 已跑，主要来源 | `tools/scrape_78dm.py` → `POST /products/bulk` | 万代/国模正式目录（含 RG 全系、MG、PB） |
| B站视频（ASR + LLM） | 已跑，KO 新品的补充 | `tools/` 流水线 → CSV → 批量导入；需要人逐条判断时进 `review_items` | KO / 第三方厂的新品、预售、价格 |
| 百度百科 / 网页整理 | 零星使用 | 手工整理 → 批量导入 | 大班等厂商的历史型号 |
| agent 网络搜索 | **未落地** | 未定 | — |
| 人工录入 | 随时 | `/#directory` 录入、`/#admin` 新增 | 补录、纠错 |

判据：**任何来源都只负责产出干净字段，不负责解析。** CSV/Excel/JSON 解析、格式校验留在 `tools/`，
API 只接受干净的 `ProductCreate`。

## 二、每条来源必须遵守的写入约定

1. **先解析身份，再写库。** `manufacturer_id` 必需、`product_line_id` 可选，且系列必须属于该厂家。
   不允许用自由文本厂名匹配，不允许自动创建厂家。匹配不到就先去 `/#taxonomy` 建厂家。
2. **把来源标题写进 `aliases`。** 展示名 `kit_name` 是手工标准化的，和源站标题必然不同；
   `aliases` 是**下次重同步时的唯一安全匹配键**。多个来源名用 `;` 分隔。
3. **重同步按 `aliases` 查，不按 `kit_name` 查。** 按展示名匹配会直接造重复，这条没有例外。
4. **身份是 `(manufacturer_id, product_line_id, kit_name)`。** 同系列同名才是同一个产品；
   `product_line_id` 为空自成一组。`work` / `release_channel` / `edition` / `appearance` 是元数据，不参与身份。
5. **重复就报错，不猜。** 批量接口遇到身份重复整批回滚（409）。名称相似度不做自动合并
   （`炮装脉冲` vs `空装脉冲` 是不同 SKU）。
6. **`source` 写这次导入的可追溯标识**：来源类型或 URL 都行，当前是自由文本。

## 三、`review_items` 的边界

```
视频抽取出 mention → review_items（pending）
      ├─ 映射 → 关联已有产品，只写 product_id/state，绝不改产品字段
      ├─ 新建 → 按表单插入 products，标 created
      └─ 跳过 → 记 skip_reason（later / ad / duplicate / invalid）
```

- 四个状态 `pending / mapped / created / skipped`，四个跳过理由。**没有第五个。**
- `later`（暂缓）是真正的积压：2026-11-05 时 571 条跳过里 514 条是 `later`，而 `pending` 只有 15 条。
  因此**侧栏 badge 显示 `pending + later`**——只显示 pending 会让队列看起来永远是空的。
- `event_date` 是「这条信息被观察到的日子」（日报期数），**不是事件日期**，不承载资讯语义。
- 这一节只描述现状。**不要为了「通用」把它改造成跨来源收件箱**：只有出现第二条也需要人审的通道
  （例如 agent 搜索真的产出了待审结果）时，才值得把它泛化成 `source_kind + source_ref + payload + decision`。
  现在改是猜。

## 四、事件 / 资讯的边界（未来）

现在不建表。落地下限如下，写在这里是为了避免下次把它塞进已有的表：

- 一张独立的 `news` / `events` 表（标题、日期、来源链接、摘要）。
- 与产品的关系是**从事件指向产品**（一张事件提及 N 个产品），产品表不加列。
- 一条资讯可以提及还没有录入的产品 → 那只是文本，**不产生占位产品**。
- 与 `review_items` 的关系也没有：视频来源的收件箱处理的是「要不要录入」，不是「这条新闻讲了什么」。

## 五、`aliases` 与 `source` 的现状

**`aliases`**：2026-11-05 有值 549/2462（22%），因为历史导入只有 RG 那批 78dm 数据写过它。

- 这是**按来源分布的正常结果**，不是治理缺口。
- 新导入一律遵守第二节第 2 条，覆盖率自然随导入增长。
- 因此：**不做 aliases 回填项目，不把覆盖率当 KPI。**

**`source`**：仍是自由文本，2026-11-05 有 1951 行是 URL、511 行是渠道名，共 1351 个不同值。

- 已确认的问题：渠道（78dm / 手动录入）和出处（视频 URL / 百科 URL）混在同一列，
  且同一视频 URL 被上百个产品重复存储，无法按渠道统计。
- **暂不改**：改成 `source_kind + source_ref` 需要一次性判断 2462 行、且当前只有一个读者（人）。
  等出现「按来源统计/筛选」的真实需求，或 agent 搜索接入需要区分通道时，再做一次迁移。
- 在那之前不要再开一次「source 该怎么存」的讨论，结论就是：**已知其不足，按需再改**。

## 六、明确不做

- ❌ 把 CSV/Excel 解析、格式校验搬进 API。
- ❌ 把入库审核拆成独立子项目（产品身份会跨库分裂，同步成本远高于这张小表）。
- ❌ 在审核页/导入脚本里自动建厂家、自动合并相似名称。
- ❌ 让 `review_items` 承载资讯语义，或让 `products` 承载事件历史。
- ❌ 把 aliases 覆盖率、pending 数量当成治理指标（前者不是缺口，后者不是 KPI）。
