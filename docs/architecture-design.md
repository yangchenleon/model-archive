# 架构设计（当前阶段）

## 目标与边界

这是个人模型收藏的资产系统，不是先做全量模型百科。系统优先保证“我有什么、它属于哪个发行物、状态如何、为什么纳入或放弃收藏”可以被追溯。

当前阶段只建设后端、数据库、导入工具与管理界面前的稳定数据边界。爬虫、价格、图片、板件、系列树、多人协作不属于第一阶段。

## 分层

```text
目录主数据 catalog_items
  ├─ 实物资产 assets
  │    └─ 资产事件 asset_events
  └─ 收藏决策 collection_targets
```

`catalog_items` 是可区分的发行物：厂商、来源类型、产品线、比例、名称、版本、编号等。它不代表你是否拥有。

`assets` 是实物盒子或一组状态相同的盒子，必须指向一个既有的 `catalog_items.id`。

`collection_targets` 是某个发行物在某个收藏分组中的决定，必须指向一个既有的 `catalog_items.id`。

`asset_events` 是资产生命周期记录，必须指向一个既有的 `assets.id`。

## 身份与关系

四张表都以 UUID `id` 作为内部主键和外键。用户不会填写 UUID，也不会填写任何关系键；未来界面通过搜索、下拉选择和复选框读取 UUID 后提交关联。

早期的 `catalog_key` 与 `asset_key` 仅为旧 JSON 导入兼容而保留，不是主键，不参与关系，也不出现在普通 CSV 模板或 API 创建参数。新记录由系统生成不透明内部值。待旧导入器废弃后，应通过迁移删除这两个兼容字段。

## 数据约束

1. 资产不能反向创建目录；目录不存在时，资产导入必须失败。
2. 收藏决策不能反向创建目录；目录不存在时，收藏决策导入必须失败。
3. 事件不能反向创建资产；资产不存在或不唯一时，事件导入必须失败。
4. `来源类型`、资产状态、盒况、收藏决定、事件类型均使用受控枚举；“不知道”必须显式填写为 `待确认`，不能由空值猜测。
5. 厂商、产品线、名称和版本暂时是字符串。目录数据稳定后，厂商与产品线再拆分为独立表，并增加别名归并。

## 演进路线

### 阶段 A：目录优先

先整理 `catalog_items`。此时只需记录可区分的发行物，资产、收藏分组和事件可以为空。

### 阶段 B：资产清点

逐项把实物绑定到既有目录项，记录状态、数量、盒况和存放位置。当前 CSV 只能安全处理“同一发行物的一组资产”；同款多盒、位置变动、状态变动应留给下一阶段界面。

### 阶段 C：管理界面

建立目录搜索/新建页、资产录入页、资产详情页、收藏分组复选框和事件时间线。此阶段解决用户不应处理 UUID、外键或 CSV 关联问题。

### 阶段 D：资料库扩展

引入厂商、产品线、系列、机体原型、图片、来源证据、别名、爬虫结果和人工核验工作流。扩展必须保持目录和资产的身份不变。

## 尚未决策

- 同款多盒是否必须逐盒建资产，还是默认用 `quantity` 聚合。
- `回收` 在原日报中的语义是否代表重新购入、待回收、还是转手处理。
- 盒绘差异、纯标签差异、再版差异的目录拆分规则。
- 厂商/产品线的正式名称、别名和显示名称策略。
